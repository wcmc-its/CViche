**Required sections and content:**

**1. Title and purpose:**
```
# CViche SAML SP Registration Guide

This document provides the information needed to register CViche as a SAML 2.0 Service Provider with the Weill Cornell Medicine Identity Provider.
```

**2. SP Metadata:**
- Metadata URL: `https://<cviche-host>/api/saml/metadata`
- Explain that this endpoint returns standard SAML 2.0 SP metadata XML suitable for automated import
- Entity ID: `https://cviche.med.cornell.edu/shibboleth` (configurable via `auth_config.yaml`)
- Note: The metadata endpoint is only available when auth mode is set to `saml`

**3. Required SAML Attributes:**
Table with three columns: Attribute Name, OID, Example Value, Required

| Attribute | OID | Example Value | Required |
|-----------|-----|---------------|----------|
| mail | `urn:oid:0.9.2342.19200300.100.1.3` | `user@med.cornell.edu` | Yes |
| displayName | `urn:oid:2.16.840.1.113730.3.1.241` | `Jane Smith` | No (falls back to ePPN or mail) |
| eduPersonPrincipalName | `urn:oid:1.3.6.1.4.1.5923.1.1.1.6` | `js1234@cornell.edu` | No (used for display name fallback) |

- Note: `mail` is the ONLY required attribute. If missing, login fails with a clear error.
- Note: CViche accepts attributes in both OID format and friendly-name format. OID is preferred for interoperability.

**4. SAML Endpoints:**
| Endpoint | URL | Binding |
|----------|-----|---------|
| Assertion Consumer Service | `https://<cviche-host>/api/saml/acs` | HTTP-POST |
| Single Logout Service | `https://<cviche-host>/api/saml/logout` | HTTP-Redirect |
| SP Metadata | `https://<cviche-host>/api/saml/metadata` | HTTP-GET |

**5. Discovery Service Integration:**
- CViche uses the WCM discovery service (WAYF) at `login.weill.cornell.edu`
- The discovery service URL is configured in CViche's `auth_config.yaml` under `saml.discovery_url`
- When a user clicks "Sign in with SSO", CViche constructs a SAML AuthnRequest and redirects the user to the IdP. The discovery service URL is used by the frontend for informational display only -- the actual SAML redirect is handled by the backend via pysaml2.
- The `SIMPLESAMLPHP_SP_ENTITY_ID` registered with the discovery service must match CViche's configured entity ID

**6. SP Certificate:**
- CViche auto-generates a self-signed RSA 2048-bit certificate on first startup
- Certificate files: `sp.crt` and `sp.key` in the configured `saml.cert_dir`
- Certificate validity: 10 years
- If the IdP requires a specific certificate, replace these files with the desired key pair

**7. Enterprise Directory Group Authorization (optional):**
- When enabled, CViche checks ED group membership at login via LDAP
- Access group: users must be in this group to access CViche
- Admin group: users in this group get admin role
- Group DNs are configured in `auth_config.yaml` under `ed.access_group` and `ed.admin_group`
- LDAP connection requires environment variables: `ED_LDAP_URL`, `ED_LDAP_BIND_DN`, `ED_LDAP_BIND_PASSWORD`

**8. Testing the Integration:**
- CViche includes a mock IdP for local testing (see `docker-compose.mock-idp.yml`)
- After registration, verify: (a) user can click SSO button and be redirected to IdP, (b) after IdP authentication, user lands back in CViche with an active session, (c) user attributes (name, email) appear correctly in CViche

**9. Contact:**
- Application owner: configurable via `ed.contact_name` and `ed.contact_email` in auth_config.yaml

Code pattern (generalized from CViche's config_loader.py):
```python
"""Load auth config from YAML and seed SystemConfig DB table."""
import json, yaml
from pathlib import Path
from sqlalchemy.orm import Session
from app.models import SystemConfig  # Your key-value config model

CONFIG_PATH = Path(__file__).parent.parent / "auth_config.yaml"

def load_yaml_config() -> dict:
    with open(CONFIG_PATH) as f:
        return yaml.safe_load(f)

def seed_system_config(db: Session) -> None:
    """Seed SystemConfig from YAML. Only inserts missing keys (safe for re-runs)."""
    config = load_yaml_config()
    defaults = {
        "auth_mode": json.dumps(config.get("auth", {}).get("mode", "simple")),
        "saml_entity_id": json.dumps(config.get("saml", {}).get("entity_id", "")),
        "saml_idp_metadata_url": json.dumps(config.get("saml", {}).get("idp_metadata_url", "")),
        "saml_discovery_url": json.dumps(config.get("saml", {}).get("discovery_url", "")),
        "saml_cert_dir": json.dumps(config.get("saml", {}).get("cert_dir", "")),
        "ed_enabled": json.dumps(config.get("ed", {}).get("enabled", False)),
        "ed_access_group": json.dumps(config.get("ed", {}).get("access_group", "")),
        "ed_admin_group": json.dumps(config.get("ed", {}).get("admin_group", "")),
        # Add your app's other config keys here
    }
    for key, value in defaults.items():
        existing = db.query(SystemConfig).filter(SystemConfig.key == key).first()
        if not existing:
            db.add(SystemConfig(key=key, value=value))
    db.commit()

def get_config_value(db: Session, key: str):
    row = db.query(SystemConfig).filter(SystemConfig.key == key).first()
    return json.loads(row.value) if row else None
```

- Create a saml_client module with:

  - `_find_xmlsec1()` -- locate xmlsec1 binary across macOS (Apple Silicon + Intel) and Linux
  - `_generate_self_signed_cert(cert_dir)` -- auto-provision RSA 2048-bit SP cert with 10-year validity

- Decision point: `allow_unsolicited=True` and `want_assertions_signed=False` for development; tighten for production

**Step 3: SAML Endpoints**
- Create an APIRouter with 4 endpoints:
  - `GET /api/saml/login` -- mode guard, build AuthnRequest, redirect to IdP
  - `POST /api/saml/acs` -- receive assertion, extract attributes, JIT provision user, set session cookie
  - `GET /api/saml/metadata` -- serve SP metadata XML for IdP registration
  - `POST|GET /api/saml/logout` -- clear session cookie, redirect to login
- CSRF exemption: ACS endpoint must be exempted from CSRF middleware (IdP POSTs from external origin)
- JIT provisioning pattern: query by email, update if exists, create with role=user if new
- Include SAML binding URI string literals to avoid import coupling

**Step 4: ED Group Lookup**
- Create ed_group_lookup module with:
  - `check_ed_membership(email, access_group, admin_group, ldap_url, bind_dn, bind_password)` -- returns `{in_access_group, in_admin_group}`
  - TTLCache (cachetools, 300s TTL) for live results
  - Stale dict fallback with 30-minute safety bound for ED outage resilience
  - `get_cached_membership`, `set_cached_membership`, `get_stale_membership`, `clear_cache` functions
  - `EdUnavailableError` exception
- LDAP implementation: memberOf check primary, direct group member query as fallback
- Key decision: admin group only checked if user is in access group (admin does NOT imply access)
- LDAP injection protection: `escape_filter_chars` on all user-supplied values

**Step 5: Session Auth with Per-Request ED Revalidation**
- Create auth module with:
  - `create_session_cookie(user)` using itsdangerous URLSafeTimedSerializer
  - `get_current_user(request, db)` FastAPI dependency that:
    1. Validates session cookie
    2. Checks user.status == "active"
    3. For SAML users with ED enabled: per-request group re-check using cache-first pattern
    4. Cache hit -> use cached result
    5. Cache miss -> LDAP query -> cache result
    6. LDAP failure -> use stale cache
    7. No stale data -> 401
    8. User removed from access group -> 401
    9. Sync role from admin group membership
- Key patterns: 7-day session TTL, httpOnly + SameSite=lax cookies, CVICHE_SESSION_SECRET env var

**Step 6: Dual-Mode Config Switching**
- Public `GET /api/auth/config` endpoint (no auth required) that returns `{mode: "simple"}` or `{mode: "saml", discovery_url: "..."}`
- Mode guard on simple login: reject with 403 "sso_required" when mode is saml
- Mode guard on SAML endpoints: reject with redirect when mode is simple
- Frontend pattern: fetch /api/auth/config on load, render SSO button or email form based on mode
- Fallback: if config fetch fails, default to simple mode (email form always accessible)
